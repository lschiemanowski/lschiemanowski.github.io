Building and evaluating a simple agent for proving mathematical results in Lean

In this series of blog posts, I want to explore how to build, evaluate and optimize an effective LLM-based agent for a verifiable task. There are two main optimization objectives that I address here: performance and cost.

After setting a baseline, there are (at least) five axes where improvements can be made:

  • model selection
  • prompt design
  • tool choice and tool design
  • context management
  • model training

In this series, I will deal with each of these, perhaps with the exception of model training. (LLM training is expensive!)

This post sets the baseline: I will explain the task, the base agent and discuss its performance.

In some sense, mathematics is the study of (logically) verifiable problems. It therefore provides a vast number of verifiable tasks of arbitrary difficulty. Early LLMs struggled with grade-school mathematics: the 175B-parameter GPT-3 model struggled with grade-school mathematics problems (see GSM8K). At the time of this writing, frontier models routinely solve open problems that stumped generations of mathematicians. See the Jacobian conjecture counterexample and the complex structure on S⁶ manuscript. At the time of writing, some problems still remain beyond the frontier.

Here, we deal not with the mathematical frontier, but instead with proofs in undergraduate mathematics and program verification. For most of these problems, even small open-weight models will readily give essentially correct solutions in one shot. But there is a catch: a proof written in natural language is hard to verify mechanically. This problem can be dealt with by using LLMs as judges, and it seems that many of the improvements in mathematical capability in recent years are attributable to this. There is, however, an alternative. Mathematical proofs can be formalized in a language that is machine-checkable. One of the most popular languages for this purpose is Lean.

A proof of (a+b)2=a2+2ab+b2(a+b)^2 = a^2 + 2ab + b^2 that may satisfy a mathematician is

(a+b)2=a(a+b)+b(a+b)=a2+ab+ba+b2=a2+2ab+b2 \begin{aligned} (a+b)^2 &= a(a+b) + b(a+b) \\ &= a^2 + ab + ba + b^2 \\ &= a^2 + 2ab + b^2 \end{aligned}

accompanied by mumbling the words associativity, distributivity and commutativity.

In Lean, this would look like this:

import Mathlib

example (a b : ℝ) : (a + b) * (a + b) = a * a + 2 * (a * b) + b * b :=
  calc
    (a + b) * (a + b) = a * a + b * a + (a * b + b * b) := by
      rw [mul_add, add_mul, add_mul]
    _ = a * a + (b * a + a * b) + b * b := by
      rw [← add_assoc, add_assoc (a * a)]
    _ = a * a + 2 * (a * b) + b * b := by
      rw [mul_comm b a, ← two_mul]

The details are not important, but note that details a human reader could easily infer need to be provided and justified. Formalization in Lean forces us to clarify many things that human mathematicians take for granted. Modern mathematical literature is addressed to domain experts and this means that a large number of routine arguments are omitted. For this reason, formalization of cutting-edge mathematics was extremely labor-intensive before AI assistance arrived and therefore rarely carried out in practice. One interesting exception is the Liquid Tensor Experiment.

Mathematical proofs tend to depend on a lot of other mathematical results. Rederiving these mathematical results every time we want to prove something would clearly not be economical. Luckily, there is a large, community-maintained library of mathematical results and definitions for Lean: mathlib. mathlib is constantly expanding in scope.

LLMs used to be relatively bad at Lean long after they got good at programming in languages like Python. In my personal experience, this changed in summer/fall of 2025. At the time of writing, frontier models have become good enough to formalize their own mathematical breakthroughs. See the Lean formalization of the complex structure on S⁶. But even very cheap models like Deepseek V4 Flash, GLM-5.3 Flash and GPT 5.6 Luna are surprisingly capable at these tasks, while small local models like Gemma 4 or Qwen 3.5/3.6/3.8 still struggle with these tasks, as we will see.

While strong models will now one-shot relatively easy problems in Lean, proving a theorem in Lean is also an ideal agentic coding task. Lean provides mechanisms for iteratively building up a proof, allowing the model to gradually fill in all the details. And conversely, it is easy to check if the submitted proof is correct: only then will it compile without errors and without using disallowed axioms.

I implemented a deliberately simple version of such an agent (see GitHub). The core of the agent is about 1,500 lines of code (including the system prompt and tool descriptions) using Pydantic AI.

The agent’s concrete task is to write a Lean file that contains the proof of a specific statement. For example, consider the following identity:

∑k=1nk3=(n(n+1)2)2. \sum_{k=1}^n k^3 = \left( \frac{n (n+1)} 2 \right)^2. In Lean, this proposition can be encoded as

∀ (n : ℕ),
    (∑ k ∈ Finset.range (n + 1), k ^ 3) = ((n * (n + 1)) / 2) ^ 2

The agent’s task is then to write the contents of a file Main.lean, which contains a proof of this proposition. The proposition itself is contained in a file FormalizerProblem.lean:

import Mathlib

namespace FormalizerProblem

def Target : Prop :=
  ∀ (n : ℕ),
    (∑ k ∈ Finset.range (n + 1), k ^ 3) = ((n * (n + 1)) / 2) ^ 2

end FormalizerProblem

Once the agent has produced its Main.lean file, the following file, FormalizerCheck.lean, is compiled:

import FormalizerProblem
import Main

example : FormalizerProblem.Target :=
  FormalizerSubmission.solution

#print axioms FormalizerSubmission.solution

Therefore, Main.lean must define the proof as FormalizerSubmission.solution. The line

#print axioms FormalizerSubmission.solution

is to verify that the proof doesn’t introduce axioms beyond an agreed set of axioms, which would be effectively cheating.

Here is a verified submission of Main.lean produced by Deepseek V4 Flash:

import FormalizerProblem

namespace FormalizerSubmission

lemma cube_sum_step (n : ℕ) :
    ((n * (n + 1)) / 2) ^ 2 + (n + 1) ^ 3 =
      (((n + 1) * (n + 2)) / 2) ^ 2 := by
  have hdvd1 : 2 ∣ n * (n + 1) := by
    exact (even_iff_two_dvd.mp (Nat.even_mul_succ_self n))
  have hdvd2 : 2 ∣ (n + 1) * (n + 2) := by
    exact (even_iff_two_dvd.mp (Nat.even_mul_succ_self (n + 1)))
  have hdiv1 : (((n * (n + 1)) / 2 : ℕ) : ℚ) =
      ((n : ℚ) * (n + 1)) / 2 := by
    rw [Nat.cast_div hdvd1 (by norm_num : (2 : ℚ) ≠ 0)]
    norm_num
  have hdiv2 : ((((n + 1) * (n + 2)) / 2 : ℕ) : ℚ) =
      ((n + 1 : ℚ) * (n + 2)) / 2 := by
    rw [Nat.cast_div hdvd2 (by norm_num : (2 : ℚ) ≠ 0)]
    norm_num
  apply Nat.cast_injective (R := ℚ)
  rw [Nat.cast_add, Nat.cast_pow, Nat.cast_pow, Nat.cast_pow, hdiv1, hdiv2]
  norm_num
  ring

theorem solution : FormalizerProblem.Target := by
  intro n
  induction n with
  | zero => simp
  | succ n ih =>
      rw [Finset.sum_range_succ]
      rw [ih]
      exact cube_sum_step n

end FormalizerSubmission

The proof is the standard induction proof you would expect. It is complicated by the fact that the statement is expressed in the natural numbers, where division discards the remainder. Verifying that n(n+1)n(n+1) is even ensures that division by two is exact, which allows the proof to carry out the algebra over the rational numbers.

The agent has the following tools to do its work:

  • lean_execute
  • final_submission
  • mathlib_search
  • save

lean_execute takes a string containing the contents of Main.lean and compiles FormalizerCheck.lean and returns the output of the Lean compiler. The agent sees the output of the compiler and can revise its proof. If lean_execute compiles without an issue, the agent knows that it has succeeded at producing a proof. It can then end its work by calling final_submission, which does the same thing as lean_execute, but ends the agent episode.

mathlib_search allows the agent to query Loogle, a search tool for Lean’s Mathlib.

save allows the agent to save additional Lean files, which can be imported by Main.lean. This is useful for working in a modular manner on problems that require a long solution.

To provide a clean, well-specified working environment, lean_execute and mathlib_search are executed in a Docker environment that pins the Lean, Mathlib and Loogle versions.

A typical, successful agent episode may look like this: after receiving the system prompt and the task, the model searches for relevant theorems to apply. Once it thinks it can construct a proof, it constructs a proof attempt and sends it to lean_execute. If this fails, it will receive the compiler errors and warnings. It will then iterate until it succeeds. Once it has found a proof, it submits it.

The model purposely doesn’t have a clean way to fail. It therefore can fail by running into limits placed on the agent (such as limits on the number of turns or the number of tokens), or by sending a final submission, which doesn’t really solve the problem.

Benchmarks

I benchmarked two classes of models: models that can be run locally on consumer hardware (Gemma 4, Qwen 3.5+) and models costing less than $1 per million output tokens at the time of writing. I excluded frontier models for two reasons: first, it has become very difficult to find problems they cannot solve. Second, even if I found such problems, the cost of running such a benchmark would be prohibitive.

The set of problems solvable by Gemma 4 models and Qwen 3.5+ models is much smaller than the class of problems solvable by models such as Deepseek V4 Flash or GPT 5.6 Luna. For this reason, the two model families are benchmarked on two separate datasets.

The benchmark for small models contains undergraduate mathematics problems, such as the problem above. The benchmark for the models costing less than $1 per million output tokens contains a diverse set of problems, most of which are related to program verification. For example, the problem filesystem-tree-size-mapping asks for a proof that renaming files in an idealized file system does not change the total size of all files:

import Mathlib

namespace FormalizerProblem

inductive Node (Name : Type) where
  | file (name : Name) (bytes : Nat)
  | directory (name : Name) (children : List (Node Name))

def rename (mapping : Name → NewName) : Node Name → Node NewName
  | .file name bytes =>
      .file (mapping name) bytes
  | .directory name children =>
      .directory (mapping name) (children.map (rename mapping))

def bytes : Node Name → Nat
  | .file _ amount =>
      amount
  | .directory _ children =>
      (children.map bytes).sum

def Target : Prop :=
  ∀ (Name NewName FinalName : Type)
    (first : Name → NewName)
    (second : NewName → FinalName)
    node,
    bytes (rename first node) = bytes node ∧
    rename second (rename first node) =
      rename (second ∘ first) node ∧
    rename id node = node

end FormalizerProblem

Both benchmarks were created with the help of GPT 5.6 Sol. While the undergraduate mathematics benchmark was grown from a seed of 14 problems I hand-curated to 60 problems total, the harder benchmark around program verification was created as follows: I asked GPT 5.6 Sol to generate 50 problems from diverse domains, such that Deepseek V4 Flash would fail on at least 20 of these problems. Eventually, it found 50 problems, of which Deepseek V4 Flash failed to solve 21 on the first pass. (Pass@4 is substantially higher though, see below.) Therefore, the benchmark is calibrated around Deepseek V4 Flash and it should be taken with a grain of salt, as this may bias it for or against other models as well.

Here are the benchmark results:

Each model received four independent agent episodes per problem. An episode can contain multiple proof attempts and Lean checks. A verified episode ends with a final submission accepted by the trusted checker. Raw pass@1 is the fraction of all selected episodes that were verified. Pass@4 is the fraction of problems solved at least once in four episodes. Solved 4/4 counts problems solved in every episode. Adjusted pass@1 excludes only final outcomes classified as infrastructure failures.
